### 📝 End-to-End 통합 QA 테스트 케이스 목록 (F-02 & SSI 연동)

아래는 핵심 사용자 여정(User Journey)에 따라 설계된 필수 테스트 시나리오입니다. 모든 단계에서 데이터 일관성과 UI/UX의 감성적 흐름을 검증해야 합니다.

#### 1. 초기 진단 및 랜딩 (Diagnosis & Landing Phase)
*   **TC-1.1 (Happy Path):** 정상적인 입력 데이터(예: $599+ Master Control)를 입력하고, SSI 시각화 컴포넌트가 성공적으로 초기 상태(불안정)를 렌더링하는지 확인한다.
*   **TC-1.2 (Edge Case):** 최소/최대 허용 범위의 데이터 입력 및 비정상적인 값(예: 0 또는 음수)을 입력했을 때, 시스템이 명확하고 전문적인 에러 메시지를 제공하며 상태 변화를 유도하는지 검증한다.
*   **TC-1.3 (Trust Widget Check):** 진단 결과가 나오기 전후로 'Rich Gold' 색상과 Trust Widget이 시각적으로 일관성 있게 배치되며, '불안정' 상태에서 '신뢰' 상태로의 시각적 전환(애니메이션)이 매끄럽게 작동하는지 확인한다.

#### 2. 가치 제안 및 전환 (Value Proposition & Conversion Phase)
*   **TC-2.1 (Premium Flow):** $599+ Master Control 티어를 선택하고 결제 플로우로 진입했을 때, `premium_value_proposition` 데이터가 백엔드 API에 정확히 전달되는지 확인한다.
*   **TC-2.2 (API Contract Check):** 프론트엔드가 요청한 데이터(예: SSI 관련 메타데이터)가 백엔드의 최종 응답과 완벽하게 매칭되는지, 그리고 `StoryFlowSchema`의 조건부 로직이 이 데이터를 기반으로 올바르게 렌더링하는지 검증한다.
*   **TC-2.3 (Session Persistence):** 사용자가 결제 과정에서 잠시 이탈했다가 복귀했을 때, 이전의 SSI 상태(불안정 단계)가 세션 데이터에 안전하게 유지되며, 재진입 시 흐름이 끊기지 않고 재개되는지 확인한다.

#### 3. 최종 결제 및 안정화 (Payment & Stabilization Phase)
*   **TC-3.1 (Successful Transaction):** 모든 금융 정보 입력 후 결제가 성공적으로 완료되었을 때, 시스템이 즉시 '통제권 회복(안착)' 상태로 전환하고, 감사 로그가 기록되는지 확인한다.
*   **TC-3.2 (Rollback Check):** 결제 실패 시나리오(아래 오류 시나리오 참조) 발생 시, 시스템이 임시 데이터 유실 없이 사용자에게 명확한 재시도 안내를 제공하며 UI가 안정적으로 유지되는지 검증한다.
*   **TC-3.3 (Post-Purchase Flow):** 결제 완료 후, 사용자가 즉시 다음 단계(예: 리포트 다운로드)로 이동할 수 있으며, 모든 관련 데이터가 DB에 영구적으로 기록되었는지 확인한다.

### 🚨 가장 취약한 3가지 오류 시나리오 (Error Handling Focus)

시스템의 안정성과 수익 흐름을 보호하기 위해 다음 세 가지 상황에 대한 에러 핸들링 로직을 최우선으로 검증해야 합니다.

#### 1. 트래픽 급증 및 동시 요청 실패 (High Traffic & Concurrency Failure)
*   **시나리오:** 대량의 사용자가 동시에 SSI 시각화 컴포넌트(실시간 데이터 스트리밍 포함)와 결제 API(`F-02`)를 호출할 때, 서버 리소스가 포화되어 발생하는 동시성 오류 또는 타임아웃.
*   **검증 목표:** 시스템이 **Rate Limiting**을 적절히 적용하고, 실패한 요청에 대해 사용자에게 '잠시 후 다시 시도해 주세요'와 같은 비침해적인 메시지를 제공하며 세션 데이터를 롤백하지 않고 유지해야 한다. (데이터 일관성 최우선)

#### 2. 결제 게이트웨이 실패 및 데이터 불일치 (Payment Gateway Failure & Data Inconsistency)
*   **시나리오:** 사용자가 결제를 시도했으나, 외부 결제 시스템(PG)과의 통신 오류 또는 승인 실패가 발생한 경우.
*   **검증 목표:** **트랜잭션 원자성(Atomicity)**을 보장해야 한다. PG 실패 시, 서버 측의 주문 상태는 '대기(Pending)'로 명확히 기록되어야 하며, 프론트엔드는 사용자에게 "결제에 실패했습니다. 시스템이 안전하게 대기 중입니다. 관리자에게 문의하세요."와 같은 구체적인 안내를 제공해야 한다. 데이터베이스와 UI 간의 불일치가 절대 발생해서는 안 된다.

#### 3. SSI 데이터 유효성 검사 실패 (SSI Data Validation Failure)
*   **시나리오:** 사용자 입력 데이터가 예상 범위를 벗어나거나, 백엔드에서 계산된 SSI 값이 프론트엔드가 기대하는 `StoryFlowSchema`의 조건부 로직과 충돌할 때.
*   **검증 목표:** 클라이언트와 서버 간의 **데이터 유효성 검사(Validation)** 레이어를 이중으로 구축하고, 모든 입력값에 대해 JSON Schema 기반의 엄격한 검증을 수행해야 한다. 실패 시, 시스템은 감정적 경고 메시지 대신 기술적으로 명확한 오류 코드와 함께 사용자에게 재입력을 요청하여 데이터 무결성을 확보한다.
