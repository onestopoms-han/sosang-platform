# 🛡️ Authority Flow 통합 테스트 케이스 목록 (V2.0)
**목표:** 시스템 오류 발생 시, 사용자에게 '안전 기본값 적용 $\rightarrow$ 원인 진단 $\rightarrow$ 통제권 회복'의 감성적 흐름을 성공적으로 전달하는지 검증한다.

## 🎯 섹션 1: 데이터 및 입력 유효성 검증 (Input Validation & Boundary Conditions)

| ID | 테스트 시나리오 (실패 조건) | 시스템 예상 동작 (기술적 결과) | 사용자 경험 목표 (감성적 결과) | 성공 기준 (Pass/Fail Criteria) |
| :--- | :--- | :--- | :--- | :--- |
| **1.1** | 필수 입력 필드 누락 (예: AOV 계산 시 금액 입력 생략) | 시스템이 `error_code: INPUT_MISSING`을 반환하고, 안전 기본값(Safe Default Value)으로 대체 시도. | 즉각적인 명확한 피드백 제공 및 다음 행동 유도. (인지 부하 최소화) | Safe Default가 적용되고, 사용자에게 '무엇이 부족했는지'를 명확히 알리는 안내 메시지 표시. |
| **1.2** | 경계값 초과 입력 (예: 마진 변동성 입력 시 극단적인 0 또는 음수 값 입력) | 시스템이 데이터 경계 조건(0값, 실패 등)을 감지하고 `WARN_THRESHOLD_LOW` 에러 코드를 발생시킴. | '위험'을 감지하고 잠재적 손실에 대해 선제적으로 경고. (예측 중심 전환) | 시스템이 임의의 값을 수용하지 않고, 명확한 위험 수준(Risk Level)과 함께 재검증을 요구함. |
| **1.3** | 비정상적인 데이터 형식 입력 (예: 숫자 필드에 문자열 입력) | 시스템이 `error_code: DATA_TYPE_MISMATCH`를 발생시키고, 해당 필드를 무효 처리함. | 오류가 데이터 자체의 문제가 아닌 사용자 입력 문제임을 인지하게 함. | 유효하지 않은 데이터는 시스템 프로세스를 중단시키지 않고, 해당 입력만 격리하여 사용자에게 수정 요청을 보냄. |

## 🎯 섹션 2: 외부 시스템 및 API 오류 처리 (External System & API Failure)

| ID | 테스트 시나리오 (실패 조건) | 시스템 예상 동작 (기술적 결과) | 사용자 경험 목표 (감성적 결과) | 성공 기준 (Pass/Fail Criteria) |
| :--- | :--- | :--- | :--- | :--- |
| **2.1** | 외부 API 호출 실패 (예: 데이터 서버 응답 지연 또는 500 Internal Server Error) | 시스템이 `error_code: API_FAILURE`를 발생시키고, 설정된 '안전 기본값'으로 대체하여 로직을 강행함. | 시스템이 중단되지 않고 자체적으로 복구하여 서비스 연속성을 유지함. (통제권 회복의 핵심) | 실제 데이터는 아니더라도, 시스템은 정상적인 UI/UX 흐름을 유지하며 **"일시적 오류 발생, 안전값 적용 완료"** 안내를 제공해야 함. |
| **2.2** | API 응답에 필수 데이터 누락 (예: 특정 계산 결과가 반환되지 않음) | `error_code: DATA_MISSING` 및 관련 예측 지표의 '안전 기본값'을 적용하여 최종 결과를 산출함. | 사용자는 '결과 없음'이 아닌, **'제한된 정보 기반의 최선책'**을 제공받아 다음 행동을 취할 수 있음. (Actionable Blueprint 강화) | 결과는 불완전하지만, 논리적 구조를 유지하며 안전 기본값이 명확히 표시되어야 함. |
| **2.3** | 권한/접근 오류 발생 (예: API 키 만료 또는 권한 부족 시도) | `error_code: AUTH_ERROR`를 발생시키고, 시스템이 사용자에게 직접적인 인증 문제 해결을 요청함. | 사용자는 시스템의 오류가 자신의 책임이 아닌 **외부 환경적 요인**임을 인지하고, 명확한 다음 단계(재인증 등)를 제시받음. | 시스템은 내부 오류가 아닌 외부 접근 문제를 정확히 구분하여 안내하며, 사용자에게 적절한 해결 경로를 제공함. |

## 🎯 섹션 3: 통합 및 감성 흐름 검증 (Integration & Emotional Flow Validation)

| ID | 테스트 시나리오 (복합 실패 조건) | 시스템 예상 동작 (기술적 결과) | 사용자 경험 목표 (감성적 결과) | 성공 기준 (Pass/Fail Criteria) |
| :--- | :--- | :--- | :--- | :--- |
| **3.1** | **복합 시나리오:** 입력 오류(1.3) + 외부 API 실패(2.1) 동시 발생 | 시스템은 가장 심각한 오류(`API_FAILURE`)를 최우선으로 처리하고, 안전 기본값 적용 후, 모든 오류 요인을 통합하여 간결한 최종 보고서를 제공함. | 복잡한 상황에서도 **'시스템이 통제하고 있다'**는 확신을 제공하며, 불필요한 혼란 없이 해결책에 집중하게 함. | 사용자에게 '오류가 발생했으나, 시스템은 안전하게 처리했다'는 단일 메시지를 명확히 전달함. |
| **3.2** | **불안정성 측정:** 예측 지표(Margin Volatility)와 실제 결과 간의 괴리 발생 시 | Emotion Flow Manager가 이 괴리를 감지하고, UI/UX에 '위험 경고' 레이어를 즉시 활성화하여 시각적 불안정성을 전달함. | 재무적 손실(Loss Aversion)에 대한 심리적 불안정성을 **시각적 안정감**으로 전환하여 안도감을 제공함. | 위험 지표가 임계치를 넘을 때, 단순한 텍스트 경고를 넘어 애니메이션/색상 변화로 감성적 신호를 명확히 전달해야 함. |
| **3.3** | **최종 검증:** 모든 실패 시나리오에서 '통제권 회복' 경험이 일관되게 제공되는지 확인 | 시스템의 모든 예외 처리 로직이 API 계약서와 안전 기본값 정의에 따라 100% 일치함을 확인. | 사용자는 오류 상황에서도 **시스템을 신뢰**하며 다음 행동을 취할 수 있음. (최종 목표 달성) | 테스트 케이스 목록의 모든 시나리오에서, 기술적 처리 결과와 사용자 경험 목표가 일치해야 함. |
