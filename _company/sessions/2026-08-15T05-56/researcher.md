## `RiskProcessorService` E2E 통합 테스트 케이스 목록 (최소 10개 이상)

본 테스트는 입력 데이터의 유효성 검사, 외부 API 통신 안정성, 그리고 안전 기본값(Safe Default Value) 적용 로직이 모든 예외 상황에서 올바르게 작동하는지 확인하는 것을 목표로 합니다.

### I. 핵심 시나리오 검증 (Mock Dataset 기반)

정상적인 데이터 흐름과 시스템의 주요 상태 전환을 검증합니다.

1.  **테스트 케이스 1: 정상(Success) 경로 검증**
    *   **목표:** 유효한 입력 데이터가 성공적으로 처리되었을 때, 정확한 Risk Score와 Actionable Blueprint가 반환되는지 확인합니다.
    *   **입력:** '정상' Mock Dataset (예: 안정적인 재무 상태 및 낮은 변동성).
    *   **검증 항목:** `RiskScore`가 예상 범위 내에 있는지, `ActionableBlueprint`가 논리적으로 도출되었는지 확인.

2.  **테스트 케이스 2: 경고(Warning) 경로 검증**
    *   **목표:** 시스템이 잠재적 위험을 감지하고 사용자에게 적절한 경고를 제공하는지 확인합니다.
    *   **입력:** '경고' Mock Dataset (예: 예상 이익 변동성이 일정 수준 이상).
    *   **검증 항목:** `RiskScore`가 경고 임계값에 도달했는지, 시스템이 적절한 **감성적 UX 흐름(Pain $\rightarrow$ Relief)**을 유도하는 메시지를 생성했는지 확인.

3.  **테스트 케이스 3: 위험(Critical) 경로 검증**
    *   **목표:** 심각한 위험 상황에서 시스템이 최고 수준의 경고를 발동하고 즉각적인 조치를 요구하는지 확인합니다.
    *   **입력:** '위험' Mock Dataset (예: 극심한 마진 변동성 또는 높은 손실 회피 비용).
    *   **검증 항목:** `RiskScore`가 위험 임계값을 초과했는지, **Actionable Blueprint**가 가장 시급하고 구체적인 조치(Loss Aversion 관리)를 포함하는지 확인.

### II. 기술적 예외 및 경계 조건 검증 (Negative Testing)

시스템의 안전장치와 오류 처리 메커니즘이 외부 요인에 어떻게 반응하는지 검증합니다.

4.  **테스트 케이스 4: API 연결 실패 시 폴백(Fallback) 처리**
    *   **목표:** 외부 데이터 소스(예: 금융 API)와의 통신 실패 시, 시스템이 다운되지 않고 안전 기본값으로 대체하여 사용자에게 안정적인 경험을 제공하는지 확인합니다.
    *   **입력:** 의도적으로 네트워크 연결을 차단하거나 응답 시간을 지연시켜 `API Connection Failure`를 유발합니다.
    *   **검증 항목:** 서비스가 `null` 또는 에러 대신, **'API 연결 실패' 상태 코드와 함께 미리 정의된 안전 기본값(Safe Default Value) 리포트**를 반환하는지 확인.

5.  **테스트 케이스 5: 데이터 스키마 불일치 처리**
    *   **목표:** 입력 데이터의 구조가 예상된 JSON Schema(`v2.0` 또는 시스템 표준)와 다를 경우, 프로세스가 오류를 일으키지 않고 적절히 거부하는지 확인합니다.
    *   **입력:** 필수 필드(`Margin Volatility`, `AOV`) 중 하나를 누락하거나, 숫자 대신 문자열을 입력하여 **데이터 스키마 불일치(Schema Mismatch)**를 유발합니다.
    *   **검증 항목:** 시스템이 데이터 유효성 검사 단계에서 즉시 실패 처리하고, 사용자에게 명확한 오류 메시지(`Data Schema Violation`)를 반환하는지 확인.

6.  **테스트 케이스 6: 극단적 경계값(Boundary Conditions) 테스트**
    *   **목표:** 시스템이 허용 가능한 입력 범위의 최솟값과 최댓값을 처리할 때 안정적인지 확인합니다.
    *   **입력:** `Margin Volatility`를 이론적으로 가능한 가장 큰 값 또는 가장 작은 값으로 설정합니다.
    *   **검증 항목:** 경계값에서 계산된 `RiskScore`가 논리적 오류 없이 정확하게 매핑되는지, 시스템이 오버플로우나 언더플로우 오류를 발생시키지 않는지 확인.

7.  **테스트 케이스 7: 비정상 데이터 타입 처리**
    *   **목표:** 입력 필드에 부적절한 자료형(예: 문자열, 객체)이 들어왔을 때의 안정성을 검증합니다.
    *   **입력:** 숫자여야 할 필드(`Margin Volatility`)에 비정상적인 데이터 타입(예: `{"error": "data"}`)을 삽입합니다.
    *   **검증 항목:** 시스템이 타입 변환 오류를 회피하고, 해당 데이터를 **'데이터 스키마 불일치'**로 분류하여 처리하는지 확인.

8.  **테스트 케이스 8: 안전 기본값(Safe Default Value)의 적용 검증 (핵심)**
    *   **목표:** 모든 실패 상황에서 설정된 '안전 기본값'이 올바르게 적용되어 최종 결과가 예측 가능하도록 보장합니다.
    *   **입력:** 테스트 케이스 4, 5, 7과 같은 오류 상황을 재현합니다.
    *   **검증 항목:** 시스템이 실패 시, **모든 출력 필드(`RiskScore`, `ActionableBlueprint`)에 대해 미리 정의된 안전 기본값 값이 채워져 있는지** 확인.

9.  **테스트 케이스 9: Actionable Blueprint의 논리적 일관성 검증**
    *   **목표:** 도출된 실행 계획이 입력된 위험 수준과 완벽하게 일치하는지, 즉 감성적 흐름(Emotion Flow)을 반영하는지 확인합니다.
    *   **입력:** '위험' 시나리오를 입력하고 결과물을 분석합니다.
    *   **검증 항목:** 높은 `RiskScore`에 상응하여, `ActionableBlueprint`가 **'통제권 확보 및 복구 과정(Control & Recovery)'**에 초점을 맞춘 구체적이고 실행 가능한 단계를 포함하는지 확인.

10. **테스트 케이스 10: 다중 데이터 통합 검증 (End-to-End)**
    *   **목표:** 여러 입력 소스(예: 재무 데이터, 시장 트렌드)가 동시에 `RiskProcessorService`에 통합되었을 때의 최종 결과 일관성을 확인합니다.
    *   **입력:** 상이한 출처의 데이터를 조합하여 테스트를 진행합니다.
    *   **검증 항목:** 여러 입력 소스가 충돌하지 않고, **최종 Risk Score가 모든 입력 요소의 가중치에 따라 합리적으로 도출**되었는지 확인.
