### 3. StoryFlowSchema v2.0 기반 예외 처리 분석 (Edge Case Checklist)

`StoryFlowSchema v2.0`는 사용자 여정(L1 $\to$ L2 $\to$ L3)을 정의합니다. 이 흐름에서 발생하는 오류를 다음과 같이 분류하고 대응 방안을 제시합니다.

#### A. 유효성 검증 실패 (Validation Failure)
*   **경계 조건 1: 비논리적 단계 전환 시도**
    *   **시나리오:** 사용자가 이미 L3 상태인데, L2로 다운그레이드(L3 $\to$ L2)를 시도하거나, 미결제 상태에서 단가 변경을 시도.
    *   **필요 조치:** 백엔드 API는 요청된 이전 단계의 유효성을 확인하고, 불가능한 전환 요청에 대해 **`400 Bad Request (Invalid State Transition)`** 에러를 반환해야 합니다. 프론트엔드는 이 응답을 받아 즉시 사용자에게 "이 경로는 허용되지 않습니다"라는 명확한 메시지를 제공해야 합니다.
*   **경계 조건 2: 가격/번들 충돌**
    *   **시나리오:** 특정 번들(Bundle) 구매 시, 시스템 내의 재고 또는 설정된 차등 단가 규칙과 충돌하는 가격이 계산될 때.
    *   **필요 조치:** `roiCalculator.ts` 내에서 모든 경로에 대해 **최종 검증 루프**를 실행해야 합니다. 데이터베이스 트랜잭션 레벨에서 이 로직을 묶어 처리하여, 한 번의 요청으로 가격과 재고 상태가 모두 일관되게 업데이트되도록 보장합니다.

#### B. 시스템 오류 및 예외 (System Errors & Exceptions)
*   **경계 조건 3: 데이터 동기화 실패 (Race Condition)**
    *   **시나리오:** 사용자가 두 개의 가격 변경 요청을 거의 동시에 발생시켜, 시스템이 L2 상태를 업데이트하는 도중에 다른 로직이 개입하여 데이터가 불일치하는 경우.
    *   **필요 조치:** 모든 가격 및 번들 변동은 **원자적(Atomic)** 트랜잭션으로 묶여야 합니다. (DB Lock 또는 Optimistic Locking 사용) 이는 AOV 극대화 로직의 무결성을 지키는 데 필수적입니다.
*   **경계 조건 4: 외부 시스템 연동 실패**
    *   **시나리오:** 가격 변동에 영향을 미치는 외부 데이터(예: 실시간 시장 데이터, 재고 API) 호출이 실패했을 때.
    *   **필요 조치:** 외부 API 호출은 **안전 장치(Fail-safe)**를 두어야 합니다. 외부 데이터가 없으면 시스템은 마지막으로 확인된 내부 기준으로 가격을 유지하거나, 명확한 오류 메시지와 함께 사용자에게 알림을 제공해야 합니다. (데이터 부족으로 분석 보류 방지)

### 4. 기술적 결론 및 권장 사항
현재 설계 방향(`StoryFlowSchema v2.0`)은 **'상태 변화의 논리적 흐름'**에 강력하게 초점을 맞추고 있습니다. 기술적 안정성을 확보하기 위해서는 다음 두 가지를 최우선으로 구현해야 합니다.

1.  **백엔드 중심의 원자성 보장 (Atomicity Guarantee):** 가격과 번들 변동은 반드시 하나의 트랜잭션 내에서 처리되어야 하며, 데이터베이스 레벨에서 동시성 문제를 완벽히 차단해야 합니다.
2.  **프론트엔드의 신뢰도 강화:** 프론트엔드에서는 API 응답 외에 서버로부터 받은 **상태 코드와 오류 메시지**를 기반으로 사용자에게 '시스템이 현재 어떤 상태인지'를 명확하게 전달하는 UI (예: `Critical`, `Warning` 게이지 시스템)를 최우선적으로 구현해야 합니다.
