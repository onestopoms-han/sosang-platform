# 🚀 쇼핑몰 MVP 최종 성능 검증 계획 (Load Testing Plan)

## I. 시스템 목표 정의
*   **주요 목표:** 대규모 트래픽 유입 시, 핵심 인터랙티브 컴포넌트(SSI)의 응답 지연 시간(Latency)을 허용 가능한 수준(예: P95 < 500ms)으로 유지하며 전체 시스템 안정성을 확보한다.
*   **핵심 검증 대상:** API Gateway $\rightarrow$ Service Layer $\rightarrow$ Database $\rightarrow$ Frontend Rendering (특히 SSI 데이터 로딩 경로).

## II. 부하 테스트 시나리오 설계 원칙
1.  **실제 사용자 여정 모방:** 단순 요청이 아닌, 실제 구매 결정 과정(불안정 $\rightarrow$ 신뢰 $\rightarrow$ 통제)을 반영하는 동시 접속 패턴을 시뮬레이션한다.
2.  **데이터 의존성 검증:** SSI 컴포넌트가 요구하는 모든 데이터(사용자 프로필, 제품 정보, 진단 결과 등)를 동시에 요청할 때의 병목 지점을 식별한다.
3.  **경계 조건 테스트:** 동시 접속자가 최대치에 도달했을 때 시스템이 어떻게 실패하고 복구하는지 (Error Handling & Fallback)를 검증한다.

## III. 아키텍처 레벨 부하 테스트 케이스 3가지

### 테스트 케이스 1: 동시 사용자 기반 SSI 데이터 요청 병목 테스트 (Concurrency Bottleneck Test)
**목표:** 시스템이 동시에 수많은 사용자 세션에서 SSI에 필요한 복합 데이터를 요청할 때, 백엔드 API와 데이터베이스의 병목 지점을 식별한다.

*   **시나리오:** **동시 접속자 500명**을 설정하고, 이들이 동시에 쇼핑몰 페이지에 접속하여 'SSI 인터랙티브 컴포넌트'를 로드하도록 요청한다. 각 사용자는 고유한 가상 사용자 ID와 특정 제품 정보를 요구해야 한다.
*   **검증 항목:**
    1.  API Gateway에서 서비스 레이어로의 부하 분산이 원활한지 확인.
    2.  데이터베이스(DB) 쿼리 지연 시간이 급증하는 구간(Slow Query)을 식별한다.
    3.  SSI 컴포넌트가 모든 필요한 데이터를 성공적으로 수신하고, **응답 시간(Latency)**이 P95 기준치(예: 500ms 이하)를 초과하지 않는지 측정한다.

### 테스트 케이스 2: 복합 상태 전환 기반 로직 부하 테스트 (Business Logic Stress Test)
**목표:** SSI 컴포넌트가 단순 데이터 표시를 넘어, `StoryFlowSchema`에 정의된 **복잡한 조건부 로직(State Transition)**을 처리할 때의 안정성을 검증한다.

*   **시나리오:** **100명**의 사용자가 동시에 여러 단계의 코칭 시나리오(`Diagnosis` $\rightarrow$ `Action Plan` $\rightarrow$ `Result View`)를 순차적으로 진행하도록 트래픽을 유도한다.
*   **검증 항목:**
    1.  백엔드 서비스가 상태 변화 로직을 처리하는 데 필요한 CPU 및 메모리 사용량을 모니터링한다.
    2.  특정 사용자 경로에서 **상태 불일치(State Inconsistency)**나 비정상적인 에러 코드가 발생하는지 확인한다. (예: 한 사용자의 데이터 요청이 다른 사용자의 세션에 영향을 미치는지)
    3.  복잡한 로직 처리 중 시스템이 멈추거나 타임아웃되는 지점을 검출한다.

### 테스트 케이스 3: End-to-End 트랜잭션 안정성 및 오류 핸들링 테스트 (E2E Stability Test)
**목표:** 사용자 경험의 시작부터 끝까지(로그인 $\rightarrow$ 상품 탐색 $\rightarrow$ SSI 상호작용 $\rightarrow$ 결제 시도) 모든 단계에서 데이터 무결성과 에러 처리 로직이 완벽하게 작동하는지 최종 검증한다.

*   **시나리오:** **200명**의 가상 사용자가 실제와 유사한 경로(로그인 후, 특정 제품 페이지 진입 $\rightarrow$ SSI 상호작용 $\rightarrow$ 장바구니 추가 $\rightarrow$ 결제 모듈 접근)를 순차적으로 수행하도록 시뮬레이션한다.
*   **검증 항목:**
    1.  **트랜잭션 성공률(Success Rate):** 전체 트랜잭션 중 실패하거나 롤백된 비율을 측정한다. (목표: 0%)
    2.  **에러 핸들링 검증:** 결제 실패, 재고 부족 등 예외 시나리오 발생 시, 시스템이 사용자에게 명확하고 '통제권 회복' 감정에 맞는 메시지를 제공하는지 확인한다.
    3.  **리소스 누수 점검:** 테스트 종료 후에도 서버 리소스(DB 연결, 메모리)가 정상적으로 해제되는지 확인하여 잠재적인 자원 누수를 방지한다.
